# 私信

个人赛和团队赛都有私信：玩家可以给其他玩家写信，除收件人外，其他玩家看不到。本文写私信的规则、格式、送达、日志和取舍。规则正文以 `RULES.template.md` 为准，团队赛的其他规则见 `docs/team-mode.md`。

## 规则

开局发言、每天出价和局末发言时，每人最多写 2 封信，每封写给 1 名其他玩家，同一名玩家最多 1 封，也可以不写。整理记忆、最终感言和观众总结时不写信。

信一律在收件人的下一次请求里送达。全员按同一串请求进行，下一次请求对每个人都是同一个环节：

| 写信时 | 收信时 |
| --- | --- |
| 开局发言 | 第 1 局开局规划（含第 1 天出价） |
| 第 N 天出价 | 第 N+1 天出价 |
| 每局最后一天出价 | 局末发言；最后一局为最终感言 |
| 局末发言 | 整理记忆，和其他玩家的局末发言一起 |

整理记忆不写信，所以第 2 局起的开局规划收不到信。两局之间的私下沟通只有局末发言时写的信，下一局还要用的内容由收件人写进记忆。

规则正文见 `RULES.template.md` 第五节第 3–7 条。

送达时机除了写在规则第 6 条，写信和收信时还各提醒一次，写法见"格式"和"收信"两节。只写在规则里不够：测试赛里有人在出价时写信，要对方"今天"避开某个价位；收信人也把出价后才收到的信，说成看过信才出的价。

## 格式

沿用 `auction_game/agent/text_output.py` 的分块格式。私信块放在原有两块之后，标签是收件人的名字：

```
<strategy>
仅自己可见的出价分析和策略，可正常分段。
</strategy>
<decision>
{"bid": 正常出价, "super_bid": 超级出价或 null}
</decision>
<收件人名字>
只有收件人能看到的私信。
</收件人名字>
```

- 不写信就没有私信块。发言的格式同样在 strategy 和 speech 之后接私信块；最终感言的格式只有 strategy 和 speech。
- 格式说明里列出其他玩家的名字，写明私信块可以不写、最多两块、收件人不能重复、每封 200 字左右，以及"收件人下一次行动时才收到，影响不了对方这一次的出价或发言"。
- 规划请求和发言请求附完整格式。第 2 天起的出价请求只附一句"请按本局规划时的格式提交：strategy 和 decision 两块，私信块可以不写，收件人下一次行动时才收到。"，因为每次都附完整格式太长，而本局规划请求留在对话里，直到局末整理记忆才清空。纠错时附完整格式。
- 长度只写在提示里，程序不检查，原因同发言字数：检查会占用唯一一次纠错机会，失败还会让整场暂停。
- 以下算格式错误，和出价违规共用一次纠错机会：收件人是自己；超过两块；同一收件人两块；私信块正文为空。
- 解析时只把单独占一行、名字是本场玩家的标签当作块的边界。开始、结束标签的名字都写错时，整块按块外文字报错，报错提示写明私信标签必须是其他玩家的名字；只写错一侧时，报开始和结束标签对不上。两种报错后面都接完整格式，格式里列有可写的名字。正文里单独一行写成某个玩家名字的标签，也会被当作块的边界而报格式错误。

### 名字

玩家名就是私信标签。阵容配置可以给每名玩家单独写名字，不写时用模型目录里的角色名。同一个模型放多名玩家时，靠这个字段区分。

读取配置时检查最终使用的名字，包括目录里的角色名：是非空字符串，不含空白和 `<`、`>`、`/`，不能是 `strategy`、`decision`、`speech`，同一场不重名。

## 收信

收到的信接在请求的事实信息之后、任务提示之前，写法和其他玩家的公开发言一致，标题写明信是在哪一环节写的：

```
以下是其他玩家昨天出价时写给你的私信：

【甲】……
```

没有收到信时没有这一段。每个请求收到的信都来自收件人上一次行动的那一轮，所以标题按请求固定：

| 请求 | 标题里的写信环节 |
| --- | --- |
| 第 1 局规划 | 在开局发言时 |
| 第 2 天起的出价 | 昨天出价时 |
| 局末发言、最终感言 | 在本局最后一天出价时 |
| 整理记忆 | 在局末发言时 |

规划请求同时交了第 1 天的出价，所以第 2 天收到的规划信也是"昨天出价时"写的；一天一局时，局末发言或最终感言收到的规划信是"在本局最后一天出价时"写的。

整理记忆的请求里，这一段接在其他玩家的局末发言之后。提示里写明：整理时结合公开发言和私信；下一局看不到之前各局的原始对话、公开发言和私信；私信里谈好的约定和得到的消息，下一局还用得上的也记下来。

## 人设

人设约束发言和私信的口吻。私信写给其他玩家，观众也会看。系统提示里的人设本来就没有限定只用于发言，提示不用改。

## 送达

- 待送达的信放在一个邮箱里。每一轮开始前从邮箱读出这一轮要送达的信，作为这一轮任务的固定输入，邮箱本身不变；这一轮结果提交后，才一次性去掉已送达的信、放进这一轮新写的信。所以补跑的任务看不到同一轮其他人刚写的信；中途退出时，邮箱仍是轮开始时的状态。
- 局末发言时写的信在整理记忆时送达。整理记忆后对话清空，信的原文不再保留。

## 日志

- `players/`：写信人的结果里多一节"私信"，收信人的请求里有收到的信。
- `letters.md`：每轮结果提交后，有人写信就追加一节，标题是写信那一轮的名称，每封信写成"【甲 → 乙】内容"，写信人按配置顺序。文件开头说明信在收件人下一次行动时收到，免得把节标题读成收信的时候。第一次有人写信时创建；场次 README 和 `speeches.md` 一样，在每局结束更新时加上链接。
- `speeches.md` 只放公开发言和观众总结，`matches.md` 只放出价表和排名。
- 终端不打印私信，一天最多 12 封，太长。

## 时序的取舍

| 方案 | 做法 | 每人每天多的请求 | 问题 |
| --- | --- | --- | --- |
| A（采用） | 信附在已有请求的回复里，收件人下一次请求时看到 | 0 | 同时写，晚一轮才到 |
| B | 每天出价前加一轮讨论 | 1，要消除冲突得两轮 | 讨论时互相看不到，看到后又各自同时出价 |
| C | 队内轮流，每天轮换顺序，后手当场看到前手的信 | 0，但一天要等三批 | 先手每天替全队定方案，变成先手指挥另外两人 |
| D | 事件驱动：有新信就唤醒，安静后结算，出价可改 | 不定 | 和控制器按轮暂停、回滚冲突，请求数没有上限 |
| E | 轮值队长先发方案并出价，另两人再出价 | 0，一天等两批 | 接近每天换人的指挥官 |

选 A：所有模式规则相同，改动小，能先在个人赛里测。

A 的弱点是同一轮里大家同时写信、看不到彼此，信又晚一轮才到。[DPBench](https://arxiv.org/abs/2602.13255) 在多个模型同时抢资源的任务里测到：同时行动时只交流一轮，死锁率基本不变（Gemini 2.5 Flash 为 86.7%）；先交流三轮，或者改成按顺序行动，才明显降低。团队赛里这可能表现为队友撞车和分工冲突。

## 送分

命中得 1 分，悬赏正好抵掉狙击的花费；被命中的一方只损失出价的金币和当天争拍卖的机会，出价 0 被命中不扣金币。所以"我出 0 让你狙"几乎是白送一分。有了私信，玩家可以私下约定互相送分。

`logs/archive_20261018/20261018_213717_ai`、`logs/archive_20261028/20261020_210047_ai` 和 `logs/archive_20261028/20261026_190107_ai` 三场只有公开发言，共 60 天，只有一次两人当天互相命中对方独占的价位，是最后一天分别出 11 和 12 的正常争夺；命中 0 的超级出价 2 次。

按 `20261018_213717_ai` 的平均值粗估：每人每天拍卖分 0.43、命中分 0.29，每局 3.6 分；每天发出的拍卖分 2.56，由参与拍卖的人平分。

| 做法 | 成员每局 | 局外人每局 |
| --- | --- | --- |
| 两人每天互狙（A 出 0、狙 1；B 出 1、狙 0） | 5.0 | 4.7 |
| 两人轮流送分（一人出 0，另一人狙 0，第二天对调） | 4.5 | 4.0 |
| 三人轮流（一人出 0，另两人狙 0） | 5.5 | 4.0 |
| 五人轮流（一人出 0，另四人狙 0） | 6.3 | 4.0 |

- 送分的人当天退出拍卖，局外人的拍卖分跟着涨，所以两人约定几乎没有优势；三人以上每局多 1–2 分。
- 表里假设局外人不跟着狙。送分的价位固定时，局外人跟着狙也能稳拿 1 分，差距会缩小；约定的人可以每天私下换价位，送分的人要多花几枚金币。

暂不处理：

- 冠军只有一个。送分约定让成员一起涨分，成员之间仍是对手，越到后面越有人想反悔。
- 两人约定只能拿到平均分，争不了冠军；三人以上要多名玩家长期守约，模型会不会这样做要看测试赛。

团队赛不受影响：两个阵营之间是零和的，跨阵营约定里一方多得的分就是另一方的相对损失，不会两边都占便宜，对称互送时分差不变；队友之间的命中按阵营规则不算。3 个以上阵营时，两个阵营可以联手送分压过第三方，问题会重新出现。

测试赛里出现三人以上的送分约定时，候选办法：

- **命中改成转移分数**：被命中的玩家扣分，送分的净收益变成 0，团队赛也适用。命中不再凭空产生分数，全场总分只剩拍卖分（现在命中分占 41%）；多人出同一价、多人狙同一价位怎么扣要重新定；可能出现负分；经济参数要重调。
- **个人赛不开私信**：改动最小，私信只留给团队赛。

"0 不算命中"挡不住：送分的人改出 1，每天多花 1 金币就行。

第一场测试赛没有出现送分约定（见"测试赛结果"），这两个办法暂不采用。

## 未采用的方向

- **时序方案 B、C、D、E**：见"时序的取舍"。
- **收信段标题补一句写信时还不知道当天结果**："昨天出价时"已经说明，再加太啰嗦。
- **一封信写给多个收件人**：一封信能发给全体，等于出价期间也有了公开发言。
- **整理记忆时写信**：两局之间已有局末发言这次写信机会。
- **局末发言的信跳过整理记忆，在下一局开局规划时送达**：信的原文能留到下一局，但送达时机成了"下一次请求"的例外，整理记忆时也没法结合信的内容。
- **私信放进 `matches.md` 或 `speeches.md`**：`matches.md` 只放出价表；放进 `speeches.md`，公开发言会被每天的私信隔开。
- **终端打印私信**：太长。
- **给私信设开关**：要多维护一套没有私信的流程；需要关掉时再加。
- **行内写法 `<名字>内容</名字>`**：要为私信单独加一套解析规则，正文里出现类似标签的文字时有歧义。
- **`<letter to="名字">` 或块内首行写收件人**：前者给协议引入属性写法，后者在块里再套一层格式。

## 测试赛要看的

- 有没有送分约定，特别是三人以上轮流送分。
- 私信内容有没有写进公开发言。
- 私信引起的格式错误次数。
- 局末收到的信里还要用的约定，有没有写进记忆、下一局有没有照着做或提防。
- 观众总结的输入涨了多少。按每局的增量推算正式赛打满 10 局时，离各模型的上下文上限还有多远；余量不够时，观众总结改用最终感言的上下文，另加每局整理的记忆。
- 出价时写的信，还有没有要求对方当天怎么做；收信人有没有把晚到的信当成行动前收到。

## 测试赛结果

第一场是 `logs/20261029_223121_ai-test`：全员用测试模型 `deepseek-flash`，2 局正赛加 1 局加赛，每局 3 天。这场的请求里还没有写信、收信时的送达提醒。正式阵容的模型行为可能不同。

- **送分**：没有。全场没有人出 0，信里也没有送分约定。
- **私信的用法**：
  - 两两互不侵犯：承诺不狙对方、交换"安全价"，几乎每对玩家都谈过；
  - 联手压领先者，出现过三人互相写信约定盯住领先者的高价；
  - 最后一天有人写信请两名玩家去狙领先者，想把比赛拖进加赛；
  - 说假话：粗略比对信里自报的当天出价和实际出价，可比的 31 封里 3 封不一致，其中一次写信人当天拿下了拍卖分。宣布了安全价却不照着出的也常见，几名玩家在最终感言和观众总结里说，互报安全价反而暴露了自己的价位。
- **送达时机**：出价时写的信多数在谈以后，但有 6 封要求对方"今天"怎么做；最后一天那两封拉人狙击的信，在最终感言时才送到。收信人也有把晚到的信说成看过才出价的。
- **公开发言**：比赛进行中没有公开具体的私信内容，局末发言只泛泛邀请私信互报安全价。最终感言里有一名玩家公开了收到的信，这时比赛已经结束。
- **格式**：111 封信，平均 94 字，最长 158 字；私信引起的格式错误 0 次。
- **记忆**：每人每局的记忆都单独列了私信约定，下一局的信常写"延续上局约定"。照做、毁约和记下防备的都有。
- **观众总结的输入**：私信让每人每局多出约 1300 字，写和收各一半，约占对话历史的 15%；讨论私信也让策略和记忆变长。按正式赛每局 5 天推算，私信加上变长的策略约多 15–20%。上一场正式赛输入最多的模型 5 局用了 29 万 token，打满 10 局约 70 万，在它的 100 万上限内，所以观众总结暂不改。
